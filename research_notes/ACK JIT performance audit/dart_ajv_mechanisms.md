## 1. What does Ajv actually do, and which work is comparable with ACK?

### Takeaway

Ajv is a schema-to-JavaScript compiler, not a generic JSON-tree interpreter on every call. In the current benchmark it returns a boolean and exposes errors; ACK runs `safeParse`, which also constructs its output representation. That is a meaningful product/API comparison, but not an isolated comparison of validation algorithms or languages. [Ajv design](https://ajv.js.org/codegen.html); [benchmark adapters](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/dart/lib/adapters.dart:26); [Node adapter](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/worker.mjs:68)

### Cited Findings

- Research access date: **2026-10-08**. The observed run used Dart **3.13.4** and Node **26.4.0**, with four process repetitions, seven samples, 100 ms target warmup, and 50 ms target sample duration. These are observations, not recommended tuning values. The 12-logical-CPU machine began the run with a one-minute load average above 232. [Recorded run metadata](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/.context/benchmark-pr213-comparison/results.json)
- Installed Ajv compilation builds a code tree, invokes `gen.optimize(...)`, renders source, and calls `new Function(...)` to create the validator. This specialization happens at schema compilation, not for every validation when that validator is reused. [Installed Ajv 8.20.0 compiler](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/node_modules/ajv/lib/compile/index.ts:162); [Ajv: Code generation design](https://ajv.js.org/codegen.html)
- Ajv explicitly optimizes for compiling schemas once and validating repeatedly. Its documentation warns that passing a different schema object can cause recompilation and recommends controlling schema lifetime/reuse. [Ajv: Managing schemas](https://ajv.js.org/guide/managing-schemas.html)
- The current Node adapter uses `allErrors: true`, `strict: true`, and disables coercion, default insertion, and additional-property removal. Its successful `output()` returns the original input. Its construct+validate phase intentionally creates a new Ajv instance and compiles again, whereas ordinary validation reuses a compiled validator. [Node worker](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/worker.mjs:68)
- `allErrors` means collecting errors across rules instead of returning after the first error. Ajv's generated function initializes its error variable to `null`; the first failure creates the error array, subsequent failures append to it, and successful synchronous validation returns `errors === 0`. This supports a low-allocation successful path for the admitted keyword subset; it does **not** establish that every Ajv schema/keyword is allocation-free. [Ajv options](https://ajv.js.org/options.html#allerrors); [generated-function setup](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/node_modules/ajv/lib/compile/validate/index.ts:91); [return logic](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/node_modules/ajv/lib/compile/validate/index.ts:198); [error-array creation](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/node_modules/ajv/lib/compile/errors.ts:90)
- Ajv enables human-readable error `messages` by default; `verbose` is false by default. Thus the existing invalid-input lane already includes Ajv's normal structured error/message construction, but not downstream JSON serialization of those errors. [Ajv reporting options](https://ajv.js.org/options.html#messages); [Node timed loop and outside-loop snapshot](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/worker.mjs:153)
- For object parsing, ACK allocates a validated output map in the source, collects errors, traverses schema properties, distinguishes missing keys from present-null, creates child contexts, parses each property, scans unknown keys, and returns an unmodifiable view of its newly built map. Lists similarly build a typed list and return an unmodifiable view. Whether individual intermediate allocations survive optimized execution must be measured. [ObjectSchema](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/packages/ack/lib/src/schemas/object_schema.dart:40); [ListSchema](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/packages/ack/lib/src/schemas/list_schema.dart:33)
- ACK context paths are **already lazy**: the complete JSON Pointer is assembled in the `path` getter. Child contexts retain their parent, schema, and value. List traversal supplies an index string as both name and path segment. It is incorrect to claim ACK eagerly builds the full path on every successful child parse. [SchemaContext](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/packages/ack/lib/src/context.dart:7); [list child context](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/packages/ack/lib/src/schemas/list_schema.dart:53)
- The benchmark times each library's result/error construction, but consumes snapshot formatting outside the timing loop. Preflight checks validity, successful value equality, repeated use, and input non-mutation; those checks are not a proof that error topology, output ownership, defaults, transforms, or refinements are equivalent across engines. [Dart adapter comments and snapshots](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/dart/lib/adapters.dart:17); [Dart preflight/timed loop](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/dart/bin/worker.dart:25); [Node preflight](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/worker.mjs:97)
- Ajv defaults `loopRequired` and `loopEnum` to **200**, switching large checks to loop-based generated code. `inlineRefs` also controls function-size/specialization tradeoffs. A wide-schema benchmark can therefore cross a code-generation threshold, rather than merely add a few map lookups. [Ajv: Advanced options](https://ajv.js.org/options.html#looprequired)

### Inferences

- Treat the measured gap as a combination of **API semantics + schema execution architecture + runtime optimization + data representation + measurement conditions**. None of the inspected evidence proves an intrinsic Dart-versus-JavaScript speed limit.
- Maintain explicit contract lanes: (a) ACK's existing `safeParse` versus parser APIs; (b) JSON-Schema validity + comparable structured errors; (c) optional boolean-only/first-error diagnostics, only if such an API is separately approved. Never relabel a no-output boolean path as an improvement to the full `safeParse` contract.
- For `safeParse`, the strongest success-path hypotheses are reducing intermediate contexts/results, lazy error-container creation, duplicate lookups, repeated schema dispatch, and output-copy bookkeeping. Removing the required output construction or returning input aliases is a semantic change, not a transparent optimization.
- An error retaining a context parent chain could retain much more input than the error's shallow size suggests. Check heap retaining paths before changing this, because access to contextual values may be intentional API behavior.
- Do not explain slower ACK invalid cases by saying Ajv short-circuits at its first error: this benchmark explicitly enables Ajv `allErrors`. Conversely, allErrors does not guarantee the same number or shape of errors across libraries; validate that separately before drawing invalid-path conclusions.

### Gaps

- There is no allocation/CPU profile from the current run, so the fraction attributable to copying, dynamic dispatch, hashing, result/context allocation, regular expressions, GC, or scheduler delay is unknown.
- Exact successful-output ownership and error-shape parity were not established by the shared preflight. Those contracts need separate ACK compatibility tests before changing runtime behavior.
- The actual generated JavaScript for each admitted schema has not been captured here. Save it in a later diagnostic run using Ajv `code.source`, along with generated source size and schema hash; do not compile or dump it inside timed validation.

## 2. How do Dart JIT, JSON representation, V8, and memory affect the hypothesis?

### Takeaway

Dart's JIT can inline, specialize from feedback, and eliminate some allocations; counting source-level constructors is not equivalent to counting runtime allocations. JSON-decoded maps also differ from JavaScript objects with V8 property shapes, so generated Dart validation can remove schema-interpreter overhead without necessarily removing map lookup or output-materialization costs. [Pinned Dart VM introduction](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/docs/README.md); [Dart JSON parser](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm/lib/convert_patch.dart#L155); [V8: Fast properties](https://v8.dev/blog/fast-properties)

### Cited Findings

- The installed Dart SDK's revision file reports **`b530c21f7de367b94fb04787bfed9d8e989d75e8`**. The VM introduction, GC documentation, service protocol, and flag definitions used below were fetched at that exact revision. This is preferable to assuming every current `main` implementation detail applies to Dart 3.13.4. [Installed SDK revision](/Users/leofarias/fvm/versions/stable/bin/cache/dart-sdk/revision); [pinned SDK tree](https://github.com/dart-lang/sdk/tree/b530c21f7de367b94fb04787bfed9d8e989d75e8)
- In the documented JIT pipeline, functions initially use unoptimized compilation; execution collects feedback for optimizing compilation. Optimizations include inlining, range analysis, type propagation, load forwarding, and **allocation sinking**. Optimized code can be installed while a hot loop is running through on-stack replacement. Failed speculative assumptions can deoptimize; subsequent optimization can use new feedback. [Dart VM introduction, JIT sections](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/docs/README.md)
- The VM documents inline caches, speculative devirtualization/inlining, and fallback dispatch at more polymorphic sites. Therefore a generic traversal repeatedly dispatching among different schema classes is a plausible specialization obstacle, not proof of one; profile hot sites and inspect optimization diagnostics if needed. [Dart VM introduction, method dispatch](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/docs/README.md)
- The Dart JSON decoder returns numbers, strings, booleans, null, lists, and maps with string keys. In this installed VM implementation, object completion calls `createMapFromKeyValueListUnsafe<String, dynamic>`, which creates the VM's compact default map implementing `LinkedHashMap`. The compact-map implementation uses a hash/index lookup for `[]` and `containsKey`. These are implementation details, not a language promise about every Dart platform. [JsonDecoder API](https://api.dart.dev/dart-convert/JsonDecoder/convert.html); [pinned parser](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm/lib/convert_patch.dart#L155); [pinned compact map](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm_shared/lib/compact_hash.dart#L671); [map factory](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm_shared/lib/compact_hash.dart#L1342)
- V8 describes HiddenClasses, shared shape transitions, in-object/out-of-object property storage, and dictionary representations. It documents how same-shaped objects support efficient property access/inline caches; dictionary properties are a different representation. This explains why a constant property access in generated JavaScript is not mechanically the same operation as a Dart `Map` lookup. The article is historical architecture documentation, not a guarantee that a particular Node 26.4.0 object uses a particular representation. [V8: Fast properties, 2017](https://v8.dev/blog/fast-properties)
- V8 also documents a JSON optimization that can reuse same-hidden-class information for faster key comparisons in `JSON.parse` arrays. This is a reason to include object-shape/key-order variants and record V8 version, not a basis for attributing a measured speedup to this feature without confirming runtime version and code path. [V8: How we made JSON.stringify more than twice as fast, JSON.parse discussion](https://v8.dev/blog/json-stringify)
- Dart's pinned GC documentation describes a two-generation collector: a parallel stop-the-world semispace scavenger for the young generation and concurrent marking/sweeping or marking/parallel compaction for the old generation. V8 also documents generational collection and parallel/concurrent/incremental GC work. Neither system's GC cost can be derived from the number of live objects at only one endpoint. [Dart GC](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/docs/gc.md); [V8: Trash talk](https://v8.dev/blog/trash-talk)
- DevTools distinguishes shallow object size, retained size, heap used/capacity/external memory, and process RSS. RSS includes stack, heap, and loaded shared libraries and excludes swapped-out pages. Node similarly separates `heapUsed`, `heapTotal`, `external`, `arrayBuffers`, and RSS; `arrayBuffers` is included in `external`. [DevTools memory](https://docs.flutter.dev/tools/devtools/memory); [Node process.memoryUsage](https://nodejs.org/api/process.html#processmemoryusage)
- The installed Dart VM JSON patch supports a fused UTF-8 decoder + JSON decoder path. The current benchmark's decode+validate lane starts from an already-created language string, so it excludes file/network I/O and UTF-8 byte decoding. [Pinned `Utf8Decoder.fuse`](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm/lib/convert_patch.dart#L45); [Dart worker](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/dart/bin/worker.dart:60); [Node worker](/Users/leofarias/conductor/workspaces/ack/edinburgh-v1/benchmarks/node/worker.mjs:124)

### Inferences

- **Generated Dart source is worth a bounded experiment, not a rewrite commitment.** Produce a specialized Dart function for one static schema, execute that source with `dart run` (JIT), and compare it with existing traversal. This is build-time source generation, **not a new AOT/native-compiled measurement**. Start with a hand-written strict validator as an engineering lower-overhead reference; it is not a proven lower bound or ceiling.
- A generated function can make property names, child types, constraint order, and success/error branches explicit and remove repeated schema-node interpretation. Retain a generic fallback for schemas/refinements/codecs not supported by that specialization. Compare a specialized full-parse function as well as any separately authorized boolean diagnostic; they answer different questions.
- Generated code operating on decoded `Map`s still needs map accesses and missing-versus-null semantics. A typed-object pipeline changes the input representation and may add a conversion pass; report both conversion + validation and already-typed validation instead of hiding conversion.
- Adding `final`, casts, or inlining pragmas should not be presented as an automatic speedup. Give the JIT regular, statically understandable code, then verify the resulting hot path and code-size tradeoffs. Premature forced inlining can create excessive generated-code size; the wide-schema experiment should explicitly track that risk.
- Larger payloads remove some constant setup cost from each item's average but magnify per-node/output-allocation costs. Therefore **larger payload does not imply ACK will approach Ajv**. Plot latency against nodes and UTF-8 bytes, estimate empirical slopes, and inspect discontinuities near GC or code-generation thresholds.
- A useful diagnostic model is `T ≈ setup + decode + per-node traversal/predicates + output construction + error construction/formatting + GC + scheduling`. This is a decomposition to test, not an assertion that separate measured medians sum exactly; optimizers, caches, and GC couple the phases.
- Retained bytes after a collection answer a different question from allocation bytes per operation. Stable retained memory can coexist with substantial allocation/GC work; a rising RSS alone does not prove an ACK leak.

### Gaps

- V8's exact revision/flags were not captured in the benchmark metadata. Add `process.versions.v8` and effective relevant flags to the next JIT/Node run metadata.
- No hot call site's feedback, inlining decision, deoptimization frequency, object representation, or actual allocation elimination has been measured here. Source inspection alone cannot tell us how much of a proposed source-level reduction survives optimization.
- No claim is made that replacing `Map`s with typed objects, adding a generated backend, or using fused UTF-8 decoding is a net win for ACK's public APIs. Each needs an end-to-end experiment and compatibility checks.

## 3. Which JIT-only profiling and large-payload experiment should happen next?

### Takeaway

Use separate uninstrumented timing, CPU sampling, allocation tracing, and retention passes on an otherwise idle machine. First vary payload count while holding semantics/schema shape constant, then vary width, depth, invalidity, and decoding independently; do not launch a large Cartesian product before the pilot identifies costs. No new AOT runs are recommended or needed. [DevTools CPU overhead guidance](https://docs.flutter.dev/tools/devtools/cpu-profiler#cpu-sampling-rate); [VM service protocol](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service/service.md)

### Cited Findings

- Dart CLI applications can be launched with `dart run --pause-isolates-on-start --observe ...` for DevTools. The profiler supports Dart CLI, not just Flutter. The Flutter-specific recommendation to use a profile build is not an instruction to replace this requested Dart JIT experiment with Flutter/AOT measurements. [Dart: DevTools](https://dart.dev/tools/dart-devtools); [DevTools CPU profiler](https://docs.flutter.dev/tools/devtools/cpu-profiler)
- DevTools CPU profiling samples stacks. The documented default UI selection is 250 µs/sample; lower and higher rates trade detail for overhead and sample-buffer coverage. The buffer is normally a ring buffer, so sufficiently long recording overwrites early samples. Inclusive and self time, sample count, and the recorded phase matter more than a screenshot of one top frame. [DevTools CPU profiler](https://docs.flutter.dev/tools/devtools/cpu-profiler)
- Pinned VM-service APIs include `getCpuSamples`, whose interval uses the same monotonic clock as `Timeline.now`; `getAllocationProfile(reset, gc)`; `setTraceClassAllocation`; `getAllocationTraces`; `getMemoryUsage`; and `getVMTimeline`. **Important source/documentation conflict:** the protocol describes `accumulatedSize` and `instancesAccumulated` as cumulative-since-reset counters, but the installed SDK's implementation fills them with exactly the same current-heap census size/count as `bytesCurrent` and `instancesCurrent`. `reset:true` only updates a timestamp in that implementation. Therefore these fields must **not** be used to report total allocated bytes/op or instances/op. Before a collection, a heap census is not necessarily only reachable retained objects. [Protocol wording](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service/service.md#classheapstats); contradicted by [actual ClassTable implementation, lines 321–346](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/class_table.cc#L321); [reset implementation](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service.cc#L4737)
- **Second implementation-specific pitfall:** `getAllocationProfile` rejects a present `reset` or `gc` parameter unless its value is `true`. To request no GC/no reset, **omit that parameter**, rather than sending `false`. With `gc:true` it calls `CollectAllGarbage(kDebugging)` before printing the census. [Dart 3.13.4 service implementation, lines 4742–4766](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service.cc#L4742)
- HTTP snapshot RPCs are feasible with Python's standard library: the pinned VM service accepts GET, validates the tokenized URI, and converts the path plus query parameters into a protocol request. HTTP clients use `sendEvents:false`; use WebSocket/`package:vm_service` for event subscriptions. `--enable-vm-service=<port>/<bind-address>` and `--write-service-info=<file>` are recognized flags; the service-info file contains the advertised URI, including its token. [HTTP server request handler](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm/bin/vmservice_server.dart#L611); [HTTP client](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/sdk/lib/_internal/vm/bin/vmservice_server.dart#L92); [bind syntax](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/bin/main_options.cc#L429); [write-service-info flag](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/bin/main_options.h#L30)
- DevTools Trace Instances can select classes, run a feature, refresh, and inspect allocation call trees/bottom-up stacks. Its snapshot diff tools address retaining paths and lifetime, which are distinct from throughput profiling. [DevTools memory view](https://docs.flutter.dev/tools/devtools/memory#trace-instances-tab)
- Node offers `--cpu-prof` and `--heap-prof`; CPU sampling interval and heap sampling interval are separate controls. Heap profiles are sampled, not an exact count of every transient allocation. The default documented heap sampling interval is 512 KiB, so short, low-allocation trials can be poorly represented. [Node CLI CPU profiler](https://nodejs.org/api/cli.html#--cpu-prof); [Node CLI heap profiler](https://nodejs.org/api/cli.html#--heap-prof-interval)

Their 100 ms warmup is a wall-clock target, and batch size may increase during recorded samples when execution becomes faster. ### Inferences

#### Proposed sequence and stopping gates — recommendations, not completed measurements

1. **Establish a clean JIT-only baseline.** Finish existing tests first; do not overlap generator suites, analysis, builds, or other benchmark workers with timing. Record CPU model, power/thermal state if available, load, versions, schema/corpus/source hashes, locks, flags, runtime modes, and case order. Keep existing AOT artifacts only as historical records. Do not try to repair the contaminated historical measurements by mathematically adjusting for load average.
2. **Separate correctness from performance-process history.** Run the full oracle separately; in the timed process, warm only the relevant workload (including its declared valid/invalid/type mixture). Use one workload/configuration per fresh process for diagnosis, and retain the existing randomized/paired multi-case program as a separate application-mix benchmark. Record warmup throughput by window. Pilot 1–5 seconds of warmup, lengthen only when convergence evidence warrants it, impose a cap, and label non-stationary runs instead of discarding inconvenient samples. Record measured samples in time order; use independent processes as the unit of replication.
3. **Uninstrumented throughput pass.** Start with ACK native JIT, ACK imported JIT, and Ajv Node. Use adjacent paired revision runs with balanced AB/BA order; randomize engine order across blocks. Keep allErrors, strict-key behavior, no coercion/default insertion, and output contract fixed. Report median and process-to-process variability, ns/payload, ns/item, payload/s, and MiB/s with the byte definition stated. Do not claim narrow confidence intervals from seven correlated batches in one process.
4. **CPU diagnostic pass, not a leaderboard run.** A dedicated driver should construct schemas/data, warm the operation, mark phase boundaries using `Timeline`/`UserTag`, execute a long known operation block, and remain available long enough to export samples. Capture validate-only versus decode-only versus decode+validate separately. Inspect self/inclusive time for contexts/results, map lookup, constraint loops, imported-schema dispatch, output collection writes, regex, JSON decode, and GC/runtime frames. Begin at a modest sampling rate; save raw samples and phase intervals. For Node, capture the same operation block with `--cpu-prof`; time numbers from these instrumented processes are diagnostic only.
5. **Allocation and GC diagnostic pass.** After construction/warmup, use `getAllocationProfile` only as a current-heap census; omit false `gc/reset` parameters. Do **not** compute allocation rate from its misleading `accumulated*` fields on Dart 3.13.4. Run targeted `setTraceClassAllocation` for contexts, result wrappers, lists/maps, and selected errors separately, then export `getAllocationTraces` for a known operation window. Report observed allocation samples and stacks with sample-buffer coverage, not an assumed exhaustive byte count. Tracing can perturb execution, and the profiler explicitly has a failure path when it cannot assign an allocation sample. Correlate timeline GC events with the operation window. Do not force GC inside timed loops, and do not equate endpoint heap differences with allocated bytes. Node's sampled heap profile is likewise for diagnosis, not an exact total. [Dart allocation-sample failure path](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler.cc#L1187)
6. **Retention pass.** Capture snapshots after setup, after discarding results, and after retaining a controlled number of success/failure results; request GC where appropriate, and verify it actually occurred. Inspect retained paths from error contexts and output containers. Report shallow/retained/live heap, external memory, and RSS separately. A retained result set is an explicitly different workload from the throughput driver's one-result sink.
7. **One hypothesis, one compatible change.** Select the largest measured avoidable cost, preserve `safeParse` semantics, change one mechanism, run semantic tests, and repeat paired JIT measurements/profiles. If profiles show decode dominates end-to-end cost, a traversal-only optimization cannot plausibly eliminate most end-to-end time; quantify the measured share before selecting the next task.

| Dimension | Initial pilot | What it isolates / required guardrail |
|---|---|---|
| Array item count | 1, 50, 500, 5,000; extend to 50,000 only within measured memory/time budget | Fixed item schema; set legitimate maxItems constraints so “large valid” inputs do not accidentally become immediate constraint failures. Report actual bytes and visited nodes. |
| Payload bytes | Approximately 1 KiB, 10 KiB, 100 KiB, 1 MiB; larger only after pilot | Report UTF-8 size of the exact shared serialized corpus. Do not conflate count, long-string length, and schema growth in one series. |

| Depth | 1, 4, 16, 64, subject to explicit stack/time cap | Context/path behavior and stack growth, while holding total nodes approximately constant for a separate series. A single deep chain is not the same workload as a large shallow array. |
| Validity | all valid; one bad first/middle/last item; 1% invalid; all invalid | Keep allErrors on; record error count/topology outside timing. Add fail-fast only as a separately labeled contract if authorized. |
| Object shape | Stable keys/order; reordered keys; allowed optional omissions; strict unknown keys | Type/shape feedback and unknown-key costs. Schema/validity must agree before timing. Preserve identical serialized inputs across languages. |
| Primitive content | Current ASCII/basic numeric subset first; Unicode, escapes, long strings, numeric boundaries separately | Add shared acceptance/output oracles before broadening. A length or numeric-representation mismatch is not a performance improvement. |
| Operation | Schema construction; decoded validation/parse; string decode only; string decode+validation; bytes decode+validation; error formatting separately | Keep schema construction out of reused-validation timings. Keep string and UTF-8-byte ingestion separate, and document ownership of input/output. |
| Result lifetime | Discard except consumed current result; retain fixed K successes; retain fixed K failures | Allocation rate, promotion, and retained memory are different application behaviors. Use an application-representative checksum without JSON-encoding every result inside validation timing. |

#### Concrete minimum profiling recipe for Dart 3.13.4 — source-verified, not executed

The controller/driver below is a **proposed diagnostic implementation**, not an existing checked-in command. It preserves JIT and does not require a Dart package installation. The exact launch flags can be supplied to the installed `dart` executable before a driver's source path; specify the benchmark package configuration when launching from outside that package. Do not use `--observe` for a headless worker unless its automatic pause-on-exit behavior is intentionally handled. `--observe` implicitly adds profiler/pause/timeline flags; explicit flags give a more predictable driver lifecycle. [CLI option implementation](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/bin/main_options.cc#L463)


Use line-delimited JSON for driver commands/responses. The driver must **await asynchronous stdin input**, not block indefinitely in `readLineSync`, so its idle main isolate can process VM-service requests. It should:

1. Load data/build schema and emit `{ready, isolateId}` outside any measurement window.
2. Accept a warmup command and run the exact selected operation/type mixture; acknowledge after warmup, then return to asynchronous input wait.
3. Accept a known-N batch command and capture `startMicros = Timeline.now` immediately before the operation loop, execute N operations with an application-relevant checksum, and capture `endMicros = Timeline.now` immediately after. No RPC, JSON serialization, per-operation timer, logging, or stdin parsing belongs inside that loop.
4. Emit `{operations, checksum, startMicros, endMicros}` after the loop. Stay alive awaiting commands until the controller finishes fetching profiles and sends an explicit exit command.

A minimal Python HTTP adapter can be:

```python
import json
import urllib.parse
import urllib.request

def rpc(base_uri, method, **params):
    # base_uri includes the random auth token and ends in '/'.
    def value(x):
        if isinstance(x, bool):
            return str(x).lower()
        return str(x)
    query = urllib.parse.urlencode({k: value(v) for k, v in params.items()})
    url = base_uri.rstrip('/') + '/' + method
    if query:
        url += '?' + query
    with urllib.request.urlopen(url, timeout=30) as response:
        envelope = json.load(response)
    if 'error' in envelope:
        raise RuntimeError(envelope['error'])
    result = envelope['result']
    if result.get('type') == 'Sentinel':
        raise RuntimeError(result)
    return result
```

**Public CPU response schema:** `CpuSamples` contains `samplePeriod` (microseconds), `maxStackDepth`, `sampleCount`, `timeOriginMicros`, `timeExtentMicros`, `pid`, `functions[]`, and `samples[]`. Each sample has `tid`, `timestamp`, optional `vmTag`, `userTag`, and `truncated`, and `stack[]` indexing the response's **functions array**. Stack order is **top/leaf first**, e.g. `bar`, `foo`, `main`; it is not root first. A `ProfileFunction` has `kind`, `inclusiveTicks`, `exclusiveTicks`, `resolvedUrl`, and `function` (a Dart Function reference or NativeFunction). Use exclusive ticks for self-time attribution; inclusive ticks from callers/callees cannot be summed as independent time. Preserve raw/private fields if present, but do not assume the public response supplies code-index stacks or a `codes[]` table. Return/reported sample coverage can be smaller than the requested wall window; report count, coverage, effective samplePeriod, and truncated stacks. Allocation-trace samples additionally expose optional `identityHashCode` and `classId`, whose latter meaning is the HeapSnapshot class index, not an automatically interchangeable `classes/N` RPC object ID. [CpuSamples](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service/service.md#cpusamples); [CpuSample](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service/service.md#cpusample); [ProfileFunction](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/service/service.md#profilefunction)

**Follow-up correction after inspecting the acquired CPU profile (2026-10-08): exported stacks are a lossy view, not an exact self-PC attribution ledger.** The general advice above about exclusive ticks applies to **the original VM-reported function aggregates**, not to counts reconstructed from `samples[].stack[0]`. This distinction is directly established by the pinned implementation:

- `ProfileBuilder::IsExecutingFrame` requires raw `frame_index == 0` **and** `first_frame_executing` (or an allocation sample). `ProcessFunction` uses this predicate to increment the VM's exclusive tick count. Being the first exported function is not this predicate. [Executing-frame rule](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler_service.cc#L895); [function tick assignment](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler_service.cc#L1165)
- Later, `Profile::ProcessSampleFrameJSON` explicitly drops invisible functions and **all stub functions**: the source comment says “Don't show stubs in stack traces.” Therefore a sampled allocator/type-test stub can have real VM-reported aggregate ticks while its index never appears in any exported function stack. Recomputing from the first visible frame assigns that sample to a surviving caller instead. Even the optional private `_codeStack` serializer drops stub/allocation/type-test-stub code, so simply requesting `_code:true` does not solve this omission. [Function-stack omission](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler_service.cc#L1624); [code-stack omission](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler_service.cc#L1700)
- `PrintSamplesJSON` exports `vmTag`, `nativeEntryTag:true`, and `runtimeEntryTag:true` separately from `stack`. Those fields can identify an exit/native/runtime context that the first reported managed frame alone does not express. [Sample serialization](https://github.com/dart-lang/sdk/blob/b530c21f7de367b94fb04787bfed9d8e989d75e8/runtime/vm/profiler_service.cc#L1714)
- In the acquired ACK-1,000 profile, the raw response has **1,119** samples; post-processing selects **1,092** inside the exact worker window and excludes **27** earlier samples tagged `VM`. The raw `_ExecuteMatch` function has **9 exclusive ticks**, **212 inclusive ticks**, and appears as the first reported function in **212** samples, **203** of which carry `vmTag: RegExp_ExecuteMatch` and `nativeEntryTag:true`. That is not evidence of 212 samples executing the Dart wrapper itself. Raw `[Stub] AllocateObjectParameterized` has **61 exclusive ticks** but appears in **zero** exported function stacks. Recommended reporting labels and denominators:

| View | Accurate label | Population / restriction |
|---|---|---|
| Original `functions[].exclusiveTicks` / `inclusiveTicks` | **VM-reported aggregate exclusive/inclusive ticks** | Preserve unchanged for the original returned sample population (1,119 here). They cannot be re-windowed exactly from lossy exported stacks. They are statistical attribution, not exact nanoseconds or allocation counts. |
| Exact-window count of `stack[0]` | **Leaf-most reported function-frame samples** | Use the selected timestamp-window population; state empty-stack handling. Do not call this “self CPU”, “exclusive ticks”, or native PC attribution. |
| Exact-window count of a function appearing anywhere | **Reported-stack presence samples** | Count once per sample, not once per recursive frame. Functions overlap, so percentages are not additive. |
| Exact-window counts by `vmTag`/entry flags | **VM/native-entry-tag samples** | For example, 203 of 1,092 selected samples carry `RegExp_ExecuteMatch`; this does not identify all C++ frames or measure exact native duration. |
| Stub aggregates | **Raw VM stub ticks, original response only** | Evidence that runtime/stub work exists; no exact-window stub percentage, allocated bytes/op, or allocator call count can be recovered from the exported stacks. |

Keep these views separate and **never sum them**: a native-regex-tag sample also contains its managed caller, and a hidden stub can make its caller appear to be the first reported function. The mixed observations support a hypothesis that regex/runtime/type-check/allocation work matters, not an exact additive cost partition. Required controls, each in its own process/configuration:

- **No-op driver:** same N-loop/checksum/input selection/command serialization but no decode or validation. This estimates driver cost and shows background allocations, but subtracting noisy heap deltas still does not recover allocation rate.
- **Decode only:** `jsonDecode(sharedEncodedInputs[i])` with a consumed root length/scalar checksum, no schema traversal. Use the identical byte-for-byte JSON strings as decode+validate; retain/discard outputs under the same declared lifetime policy. The decode+validate combined result need not equal the sum of independently measured medians.
- **Validation only:** reuse decoded inputs and prepared schema, same input rotation and result-lifetime policy.
- **Decode+validation:** decode the input string every operation, then call the real API. No file reads/string generation inside the operation unless the lane explicitly intends to measure them.

These controls provide useful CPU attribution and heap-state diagnostics. They do **not** make Dart 3.13.4's `getAllocationProfile` a cumulative allocator meter; true allocation-byte accounting remains an open tooling requirement unless a separate supported profiler/counter is validated.

#### Decision criteria

- **Contexts/errors dominate allocations on valid input:** prototype a compatible internal fast success path or deferred diagnostic state, but preserve error values/paths/order and refinements that need context. Re-measure actual allocations, not source-level constructor count.
- **Map lookups dominate CPU:** inspect repeated `containsKey` + `[]`, but preserve absent versus present-null and optional/default rules. Benchmark any single-lookup design in the real generic map shape; a sentinel scheme can add its own cost.
- **Schema dispatch dominates CPU:** specialize a narrow keyword subset, with a generic fallback. Track code size, compile latency, warmup, and schema churn; Ajv's own thresholds illustrate why universal unrolling is not free.
- **Output containers dominate allocation:** reduce redundant intermediate copies/capacity growth while preserving output semantics; an optional validation-only API is a separate product decision, not an excuse to weaken `safeParse`.
- **JSON decoding dominates:** investigate fused UTF-8 ingestion and reuse/streaming only in separately defined input APIs; preserve malformed-input behavior and include decoding in end-to-end timing.
- **Results remain noisy or non-stationary:** the next useful work is a controlled run and stable profiling environment, not more decimal places or larger arbitrary payloads.
